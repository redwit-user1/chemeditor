## 1. ChemDraw SDK 없이 "붙여넣기 → 즉시 물성 계산"이 되는가

**예. E2E p50 404 ms / p95 439 ms** (Chromium 30회, 150 ms 디바운스 포함;
붙여넣기 → Ketcher 렌더 → HTTP → RDKit 계산 → 화면 갱신 전 구간).
백엔드 계산 자체는 p95 **0.31 ms**. 목표 ≤ 1초를 여유 있게 만족한다.

> **단, 이 404 ms 는 편집기가 이미 떠 있는 상태의 값이다.** 편집기가 화면에
> 나타나기까지는 별도로 **5.3초**가 걸린다(첫 방문·지연 0 기준). 두 숫자를
> 하나로 뭉치면 "1초 안에 된다" 가 현장에서 거짓이 된다. §8 에 분리해 적었다.

배포된 프로토타입에는 구조를 넣는 자리가 **두 군데**이고 의존이 다르다.

| 자리 | 계산 주체 | 외부 의존 | 실측 |
|---|---|---|---|
| 연구노트 본문의 구조 블록 | 빌드 시 RDKit 로 미리 계산해 둔 표(14종) | **없음** | 아스피린 → C9H8O4 / 180.159 / 180.0423 ✅ |
| 구조 입력기 화면(Ketcher) | RDKit 백엔드 HTTP | **있음** | 배포 백엔드 미검증(§7) |

시연 자리에서 회선이 불안하면 앞쪽 경로가 안전하다.

표시 항목은 기존 시스템과 동일하다: Mol Formula, Mol Weight, Exact Mass, Heavy Atoms.
계산 주체는 전부 RDKit(BSD) — ChemDraw SDK도, Ketcher 내장 엔진(Indigo)도 수치에
관여하지 않는다. 재단 합성노트 KJA-025-84의 stoichiometry 표(4.54 mmol / 0.464 g /
0.428 ml / 0.691 g / 37.0% / 0.908 M)가 **인쇄 자릿수까지** 재현됨을 테스트로 고정했다.

## 2. Oracle SE 제약(Cartridge 불가) 하에서 substructure 검색이 3초 내인가

**예 — 재단 현재 규모(5,342건)에서 최악 쿼리 p95 50.1 ms** (30개 대표 쿼리 × 100회,
`PortableFPBackend`). Similarity p95 14.6 ms.

이식 경로의 구성: fingerprint를 32개의 signed 64bit 정수 컬럼으로 분해 저장하고,
표준 SQL(`WHERE (fp_i & :q) = :q` — Oracle `BITAND`)로 스크리닝한 뒤 앱 레이어
RDKit이 정밀 확정한다. `bit_count`/`ARRAY`/`@>`/`%` 등 Postgres 전용 문법은 없다.

**정합성 보증:** 30개 쿼리 전부에서 브루트포스 RDKit 정답지와 결과 집합
**완전 일치**(부분집합 아님, 스크리닝 재현율 100%)를 테스트 게이트로 고정했다.

> 기술 정정 1건: SPEC §4.3의 "Morgan FP로 substructure 스크리닝" 지시는 화학적으로
> 성립하지 않아(부분구조 포함성 부재 → false negative) 스크리닝 전용으로 설계된
> PatternFingerprint로 교체했다. 상세: `docs/DECISIONS.md`.

## 3. 5,342 → 50,000 → 500,000 확장 시 어디서 깨지는가

| 규모 | Substructure 최악 p95 | Similarity p95 | ≤3s |
|---|---|---|---|
| 5,342 | 50.1 ms | 14.6 ms | ✅ |
| 50,000 | 427.0 ms | 149.7 ms | ✅ |
| 500,000 | **4,216.4 ms** | 1,795.8 ms | **❌** |

**미달을 미달로 적는다.** 500,000건에서 benzene(후보 456,448건)·toluene(339,626건)
두 광역 쿼리가 3초를 넘는다. 병목은 스크리닝이 아니라 **정밀 매칭 단계가 후보 수에
선형**(약 9 µs/후보)이라는 점이다 — 즉 임계점은 "규모"가 아니라 **후보 약 30만 건**이며,
50만 건 라이브러리에서도 선택적 쿼리(phenol 이하 28개)는 1.2~2.4초에 그친다.

개선안(미구현, 설계만 제시): ① 결과 상한(limit) 도달 시 정밀 매칭 조기 종료 —
실제 UI는 200건만 표시하므로 광역 쿼리일수록 효과가 큼, ② 후보 정밀 매칭 병렬화,
③ ring-count 등 추가 프리필터. 참고로 재단 라이브러리는 현재 5,342건이고 500k는
94배 성장 시나리오다. 500k 측정은 소요시간 사유로 쿼리당 20회 반복(기본 100회
미만)이며 표에 명시했다.

## 4. RDKit 계산값이 기존 CBOE 데이터와 일치하는가

**실데이터 미확보 — 검증 파이프라인은 완성, 수치는 픽스처 기준.** 재단 실측 SDF가
본 저장소에 없어(비공개) 전 레코드 대조는 실행하지 못했다. 파이프라인은 재단 스키마
(다중 컴포넌트 임베드 `VW_MIXTURE_STRUCTURE.STRUCTURE (n)` 레이아웃, `STRUCTUREAGGREGATION`
보존·비파싱)를 처리하며, 픽스처에서 **의도적으로 주입한 불일치 2건(염 counter-ion 누락,
저장값 오류)을 정확히 사유와 함께 검출**했다 (6/7 일치, `reports/parity.md`).
허용오차는 MolWt ±0.01, MolFormula 완전 일치로 고정했고 조정하지 않는다.
실측 SDF를 `data/`에 넣고 `make parity` 실행이 필요하다 — **이것이 회신 확정 전
반드시 남은 한 단계다.**

## 5. ChemDraw 클립보드 붙여넣기가 `.cdx` 파서 없이 동작하는가

**예.** ChemDraw는 복사 시 클립보드에 `text/plain`으로 SMILES 또는 MOL 텍스트를
함께 올린다. 본 구현의 paste 경로는 그 텍스트를 받아 RDKit이 파싱한다 — `.cdx`
바이너리 코드 경로는 존재하지 않는다(코드베이스에서 확인 가능). SMILES/MOL 텍스트
붙여넣기 → 물성 계산은 E2E로 검증했다(§1의 404 ms가 그 측정). 한계의 정직한 기재:
**실제 ChemDraw 데스크톱이 설치된 환경에서의 상호운용 확인은 본 PoC 환경(폐쇄
컨테이너)에서 수행하지 못했다.** MOL 블록 경로가 동일하므로 리스크는 낮게 보나,
파일럿 첫 주에 실기기 확인을 권장한다.

## 6. 남는 리스크는 무엇인가

**① 연구원의 그리기 UX 저항 — 정량화 불가.** Ketcher는 기능적으로 충분하지만
(그리기·템플릿·reaction 모드·단축키), ChemDraw에 10년 익은 손과는 다르다. 이것은
벤치마크로 측정할 수 없는 종류의 리스크이며, 측정할 수 없다는 사실을 그대로 적는다.
"교육으로 해결 가능합니다" 같은 근거 없는 낙관은 쓰지 않는다. 완화 수단은 파일럿
부서 우선 적용과 병행 사용 기간 확보뿐이다.

**② 재단이 지금 겪는 문제의 본질은 벤더 종속이다.** PerkinElmer(현 Revvity)
라이선스 종속이 서비스 중단으로 이어진 것이 이 사업의 출발점이다. 그 해결책으로
다시 Revvity의 ChemDraw SDK에 종속되는 것은 **같은 리스크의 재발**이다. 본 PoC의
스택(Ketcher Apache-2.0 / RDKit BSD)은 소스가 공개되어 있어 공급 중단이라는 개념
자체가 성립하지 않는다. — 이 논점을 제시하는 우리가 그 대안을 제공하는 당사자라는
**이해상충은 숨기지 않는다.** 판단 근거는 전부 본 저장소의 실측·테스트로 공개되어
있으며, 제3자가 `make test` / `make bench`로 재현할 수 있다.

**③ 처음 여는 비용 — 이번에 실제로 현장을 막았다.** 구조 입력기 첫 진입
40.8 MB · 5.3초(지연 0 기준 하한). 계산은 밀리초인데 화면이 뜨는 데 초가 걸린다.
연구원이 하루에 여러 번 여는 화면이라면 이 비용은 기능 미비와 같은 무게를 갖는다.
완화 설계는 §8 에 적었고 아직 구현하지 않았다 — **측정된 미달로 남긴다.**

**④ 운영 환경 실검증 잔여.** 이식형 백엔드는 SQLite로 실검증했고(사용 SQL 부분집합은
Oracle SE와 호환) Postgres+Cartridge 기준선은 `PG_DSN` 제공 시 동일 동치성 스위트에
편입되도록 준비되어 있으나, **Oracle SE 실계측과 Docker 스택 실기동은 본 환경(데몬
부재)에서 수행하지 못했다.** 실데이터 parity(§4)와 함께 파일럿 착수 시 최우선 항목이다.

## 7. 재단이 직접 눌러 볼 수 있는가 (2026-08-07 추가)

**예. 배포했다.** <https://chemeditor.vercel.app/lims-poc/>

기존 구노 ELN 의 실제 Thymeleaf 화면 24장을 그대로 렌더하고 그 위에 LIMS
화면을 얹은 것이다. 별도로 만든 목업이 아니라 **제품의 화면**이다.

### 기능 점검 — 18개 중 17개 통과

배포본과 동일한 빌드를, 배포와 동일한 구조(`/lims-poc/` + `/editor` rewrite,
실제 Ketcher SPA)로 세워 하나씩 눌러 확인했다.

| | 결과 |
|---|---|
| 노트 구조 블록 붙여넣기 → 물성 | ✅ C9H8O4 / 180.159 / 180.0423 |
| 구조 입력기에 실제 Ketcher 로드 | ✅ |
| 부모 화면 → 편집기 구조 주입(postMessage) | ✅ |
| 편집기 → 부모 물성 회신 | ❌ **미검증** → 2026-08-07 검증했고 **깨져 있었다**. §10 |
| 연구노트 생성 → 귀속 프로젝트 안내 | ✅ |
| 사용 안내서 열람 | ✅ |
| 시료·시험·결과입력·결과검토·기준이탈 | ✅ |
| 시약/재고·장비·보관위치·시험법 | ✅ |
| 화합물 라이브러리·프로젝트 시약/화합물 | ✅ |

**미검증 1건의 정직한 기재:** 편집기의 물성 계산은 RDKit 백엔드
(`chemeditor.srv1711580.hstgr.cloud`)를 HTTP 로 부른다. 본 작업 환경의 egress
정책이 그 호스트와 배포 도메인 모두를 차단해(정책 거부 403) **살아 있는지
확인하지 못했다.**

> **2026-08-07 후속.** 배포와 같은 구조로 거울을 세워 확인했다. 살아 있지
> 않았다 — 배포본은 정적 사이트라 `/api/v1` 자체가 없고, 편집기는 그 주소로만
> 계산하고 있었다. 즉 **이 표의 나머지 17건이 통과하는 동안 정작 이 PoC 가
> 증명해야 할 단 하나가 배포본에서 한 번도 동작한 적이 없었다.** 원인과 조치는
> §10 에 적는다.

### 현장에서 보고된 결함 2건과 조치

2026-08-06, 신약센터에서 두 가지를 알려 왔다. 둘 다 재현했고 둘 다 우리 결함이다.

**① "구조가 그려지긴 하던데 입력이 되질 않아서요, smiles 도 넣어봐도 잘 안되고"**

편집기는 정상이었다. 문제는 편집기가 안 붙었다고 **판단하는 기한이 8초**였던
것이다. 번들이 24MB 라 지연 0 인 로컬에서도 5.3초가 걸리고 실제 망에서는 8초를
넘긴다. 그래서 아직 내려받는 중인 편집기가 대체 화면(RDKit 로 미리 그려 둔 구조)
으로 갈아치워졌다 — 그림은 있고 입력은 안 되는 화면이 그것이다.
→ 시간으로 실패를 단정하지 않도록 고쳤다. 상세: `reports/bench.md`.

**② "노트도 생성해봤는데 어디에 만들어진 건지 확인이 잘 안됩니다"**

애초에 생성되지 않았다. 생성 요청은 `FormData` 로 나가는데 프로토타입의 목
서버가 쿼리스트링만 해석해 노트 이름이 유실됐다.
→ 이름이 저장되고, 확인창이 귀속 프로젝트를 명시한다.

**이 두 건이 시사하는 것:** 백엔드 성능(§1~§3)이 아무리 좋아도 **처음 화면이
뜨는 데 실패하면 사용자에게는 기능이 없는 것과 같다.** 회신서가 성능만 말하고
로딩 비용을 말하지 않으면 그 회신은 현장과 어긋난다. 그래서 §8 을 넣는다.

## 8. 처음 여는 비용 (2026-08-07 추가)

| 화면 | 첫 진입 | 전송량 |
|---|---|---|
| 대시보드 · 시료 · 화합물 · 결과검토 | 2.1 ~ 2.5 초 | 5.4 ~ 5.6 MB |
| 연구노트 작성 | 4.4 초 | 8.7 MB |
| **구조 입력기** | **8.7 초** | **40.8 MB** |

구조 편집기가 쓸 수 있게 되기까지 — 첫 방문 **5.3초**, 캐시 있는 두 번째 방문
**3.3초**(24MB 번들의 파싱·WASM 초기화 비용이라 캐시로 없어지지 않는다).

**모두 네트워크 지연 0 에서 잰 하한이다.** 재단 내부망에서는 더 걸린다.
배포 도메인 직접 계측은 egress 정책에 막혀 하지 못했다.

이 비용은 **줄일 수 있다**(RDKit WASM 지연 로드 · Ketcher 트리셰이킹 ·
번들 사전 캐시). 셋 다 설계만 제시하고 이번 PoC 에서는 구현하지 않았다 —
`reports/bench.md` 참조. **파일럿 착수 전 처리할 항목으로 본다.**

## 10. 배포본에서 메인 기능이 실제로 되는가 (2026-08-07 추가)

§7 은 "18개 중 17개 통과" 였고, 미검증 1건이 **"편집기 → 부모 물성 회신"** 이었다.
그 1건을 배포와 같은 구조(`/lims-poc/` + `/editor` rewrite, 실제 Ketcher SPA)로
세워 눌러 봤다. **되지 않았다.** 그리고 원인은 계약이 아니었다.

### 무엇이 일어나고 있었나

| 단계 | 결과 |
|---|---|
| Ketcher 로드 | ✅ `chemeditor:ready` 도달 |
| SMILES 붙여넣기 | ✅ 구조가 캔버스에 그려짐 |
| 물성 계산 | ❌ `POST /api/v1/chem/properties` → **501** |
| 부모 창 통지 | ❌ **아무것도 오지 않음** |

배포본은 정적 사이트다. `/api/v1` 이 아예 없다. 그런데 편집기는 그 주소로만
계산하도록 되어 있었고, 실패했다는 사실조차 부모에게 알리지 않았다. 그래서
Goono 쪽 화면은 "편집기 준비됨" 인 채로 물성칸이 `-` 로 남았다.

**이것이 재단이 알려 온 "구조가 그려지긴 하던데 입력이 되질 않아서요, smiles 도
넣어봐도 잘 안되고" 의 나머지 절반이다.** §7 에서는 8초 타임아웃만 원인으로
적었는데, 그것을 고쳐도 이 화면은 여전히 숫자를 못 냈다. 회신서가 §1 의
"E2E p50 404 ms" 를 근거로 "된다" 고 적는 동안, 재단이 실제로 열어 본 화면에서는
한 번도 계산된 적이 없었다.

### 조치 — RDKit 은 정본으로 두되, 닿지 못하면 말한다

Ketcher 는 Indigo(WASM)를 이미 번들에 담고 있다. RDKit 백엔드에 닿지 못했을 때만
그것으로 계산하고, **어느 엔진이 낸 값인지 화면 세 곳(편집기 하단 · 구조 입력기
팝업 · 노트 구조 블록)에 모두 적는다.**

- RDKit 이 **답을 했는데** 못 읽겠다고 하면 대체하지 않는다. 도달 실패와 구조
  오류는 다른 문제이고, 하나로 뭉개면 잘못된 구조가 조용히 통과한다.
- `reports/bench.md` · `reports/parity.md` 의 수치는 전부 RDKit 값 그대로다.
  이 대체 경로는 그 표에 들어가지 않는다.

실측(배포와 같은 구조, Indigo 경로):

| 구조 | 분자식 | 분자량 | Exact Mass | 걸린 시간 |
|---|---|---|---|---|
| 아스피린 | C9H8O4 | 180.159 | 180.0423 | 189 ms |
| 카페인 | C8H10N4O2 | 194.194 | 194.0804 | — |
| 벤젠 | C6H6 | 78.114 | 78.0470 | — |

세 값 모두 문헌값과 MolWt ±0.01 안에서 일치한다. **다만 이것은 세 건의
확인이지 대조가 아니다.** 두 엔진의 전 레코드 대조는 하지 않았다 —
염·호변이성 처리가 다르므로 어긋나는 구조가 있을 것으로 본다.
**파일럿에서는 RDKit 백엔드를 실제로 띄우는 것이 전제다.** 이 대체 경로는
정적 데모가 빈 화면을 보여 주지 않게 하기 위한 것이지, 운영 설계가 아니다.

### 같이 드러난 결함 2건

- **구조를 지워도 부모 창에 이전 분자의 숫자가 남았다.** `[화합물 등록]` 도
  눌린 채여서 **방금 지운 구조를 등록할 수 있었다.** 계약에 "비었다" 를 알리는
  메시지가 없었던 것이 원인이다.
- **노트 구조 블록이 멀쩡한 구조를 "해석하지 못했습니다" 로 적었다.** 블록은
  편집기 값을 버리고 서버에 다시 묻는데(정본 일원화), 그 서버가 없으니 빈 값이
  오고 그것을 입력 탓으로 적었다. 아스피린을 붙여넣은 사용자가 자기 SMILES 를
  의심하게 되는 문구다.

### 여기서 배운 것

§9 는 "자동 점검이 훑는 것과 사람이 쓰는 것 사이의 간격" 이었다. §10 은 그보다
나쁘다 — **점검 자체가 배포된 환경이 아닌 곳에서 돌고 있었다.** 로컬에는
백엔드가 있었고 배포본에는 없었는데, 그 차이를 아무 검사도 보지 않았다.
지금은 배포와 같은 구조로 세운 거울에서 전 화면·전 경로를 돌린다.
**회신서에 "된다" 를 적기 전에, 재단이 열 주소와 같은 모양에서 눌러 봤는지를
먼저 확인해야 한다.**

## 11. 연구노트 작성 화면을 참고 설계에 맞춰 다시 세웠다

재단이 보내 준 참고 설계(구축형 GOONO_디자인 / ELN Editor / GOONO_LIMS_Ops)를
기준으로 작성 화면을 다시 만들었다. 셋 다 눌러 볼 수 있다.

| | 무엇 | 어디서 확인 |
|---|---|---|
| A | 본문을 목적·재료·절차·결과·고찰 다섯 섹션으로 나누고 왼쪽에 아웃라인 레일 | `/lims-poc/note_write.html` |
| B | 본문에서 `/` 로 블록, `@` 로 시약 Lot·시료·장비·사람 삽입 | 같은 화면, 본문 안 |
| C | 점검 워크플로 + 시점인증 + 정정 기록 | 같은 화면, 왼쪽 패널 |

### C 는 새 기능이 아니라 제품에 있는 점검 흐름이다

처음에는 이 자리에 "검토 요청 → 승인 및 서명" 이라는 흐름을 새로 만들었다.
그러다 구노 제품에 같은 기능 — 점검 — 이 이미 있다는 지적을 받았다. 맞는
지적이었다. `Constants.java` 의 작성 상태(`WRITING → INSPECTION →
COMPLETE / REJECT`)와 점검자별 상태(`UNCONFIRM → APPROVAL / REJECT`),
노트 레이아웃의 점검 요청·점검자 지정·점검 진행 박스가 그것이다. 같은
기능이 두 이름으로 있으면 사용자는 무엇이 정본인지 알 수 없다. 걷어내고
제품 어휘·흐름으로 다시 연결했다.

```
작성 ──점검 요청(점검자 지정)──→ 점검 진행 ──전원 승인──→ 시점인증 · 완료
  ↑ 요청 철회(판정 전만)             └── 반려(사유 필수) ──→ 작성중
```

- 점검 요청은 프로젝트 멤버에서 점검자를 지정해서 낸다(복수).
- 반려 한 건이면 노트 전체가 사유와 함께 작성중으로 돌아간다.
- 전원 승인이면 점검완료 + 시점인증 — 본문이 잠기고, 남는 쓰기는 정정
  기록(원문 보존 + 덧붙임)뿐이다.
- 판정 규칙은 서버(목)가 쥔다. 화면을 우회해 점검완료 뒤 재요청을 직접
  호출했고 거부되는 것을 확인했다. 철회는 아무도 판정하지 않았을 때만 된다.

시점인증 해시는 목이 찍는 모의 값이고 화면에 `(모의)` 로 표시된다. 실제
TSA·전자서명(PKI)·역할 분리는 파일럿 항목이다(안내서 3-6).

자리도 제품 그대로다. 처음에는 본문 카드 위에 스테퍼 띠를 새로 만들었는데,
왼쪽 패널에 점검 요청 버튼과 연구노트상태 줄이 이미 있다는 지적을 받고
걷어냈다 — 같은 조작이 두 자리면 어느 쪽이 정본인지 알 수 없다. 지금은
왼쪽 패널의 그 버튼이 상태 따라 할 일을 바꾸고(점검 요청 → 철회 → 재점검
→ 정정 기록), 점검자별 진행은 왼쪽 패널의 점검 상자에 붙는다. 상단 바는
참고 크롬(ELN Editor 1a)대로 뒤로(아이콘) · 프로젝트 › 노트명 브레드크럼 ·
상태 알약 · 저장 시각 · 우측 저장으로 다시 짰다. 저장 조작과 저장 시각은
상단 바 한 곳에만 있다.

### 이 화면의 모달이 전부 눌리지 않고 있었다

C 를 검증하다 발견했다. 시약 선택 팝업(P0 기능)을 포함해 이 화면의 모달은
열리기만 하고 그 안의 어떤 것도 클릭되지 않았다. 백드롭이 위에 있었다.

```
layout.css:183  #main-body #main-body-right { position: fixed }   (>1100px)
layout.css:236  #main-body #main-body-right { position: sticky }  (≤1100px)
```

`fixed` 와 `sticky` 는 `z-index` 가 `auto` 여도 쌓임 맥락을 만든다. 모달이 그
안에 선언돼 있어 `z-index: 1060` 이 그 덩어리 안에서만 유효하고, 바깥에서는
덩어리 전체가 `auto` 다. 부트스트랩은 백드롭을 `<body>` 밑에 1050 으로 붙인다.
두 폭 모두에서 백드롭이 이긴다. 구노 제품의 노트 레이아웃을 쓰는 화면 전체가
같은 조건이다.

`layout.css` 를 고치면 제품 전체의 노트 배치가 흔들리므로 모달만 `<body>` 로
옮겼다. 백드롭과 같은 맥락에 서면 1060 이 이긴다.

이건 27개 화면 전수 점검(§9)에서 나오지 않았다. 그 점검은 모달을 **열어 보긴
했지만 열린 뒤에 눌러 보지는 않았다.** 열림은 클래스로 확인되고 눌림은
좌표로만 확인된다 — `elementFromPoint` 로 실제로 무엇이 그 자리에 있는지
보기 전까지는 통과로 나온다.

## 12. 재단 실사용 회신에 대한 검토 (2026-08-13)

합성 연구원이 프로토타입을 직접 써 보고 6개 항목을 보내 왔다. 각각 코드까지
내려가 원인을 확인했고, 판정과 근거를 아래에 적는다. **고쳤다고 적은 것은

### E-1. 화살표 위쪽 시약이 인식되지 않던 원인은 셋이었다

가장 중요한 항목이라 끝까지 파고들었고, 파 보니 원인이 하나가 아니었다.

**(1) 포맷이 파서보다 먼저 버리고 있었다.** 화학량론 패널은 `getRxn()` 으로
MDL Rxnfile 을 서버에 보냈다. 그런데 Rxnfile 에는 **agent(화살표 위 종)를
담는 자리가 없다** — V2000 도 V3000 도 그렇다. RDKit 왕복 실측:

```
반응 SMILES 로 읽으면        agents: 3   (HATU · TEA · DCM)
RXN V2000 으로 왕복한 뒤     agents: 0
RXN V3000 으로 왕복한 뒤     agents: 0
```

즉 화살표 위 시약은 파서에 닿기도 전에 **직렬화 단계에서 소멸**했다. 파서만
고쳐서는 절대 나오지 않는 종류의 결함이다. 반응 SMILES 는 가운데 자리
(`reactants>agents>products`)에 그것을 담는다 — 여기서 유일하게 왕복되는
포맷이라 전달 경로를 그쪽으로 바꿨다.

**(2) 파서도 읽지 않고 있었다.** `parse_reaction` 이 `GetReactants()` 와
`GetProducts()` 만 읽고 `GetAgents()` 를 버렸다. agent 역할을 추가했다.

**(3) 빈 목록이 두 가지 뜻을 갖고 있었다.** "화살표 위에 아무것도 안 그렸다"
와 "포맷이 담지 못한다"가 화면에서 똑같이 빈칸으로 보였다. 응답에
`input_format` 과 `agents_unsupported_in_format` 을 실어 구분한다.

**실측 (아마이드 커플링, 브라우저 → 실제 RDKit 백엔드):**

```
반응물    C14H12O3   228.247    4-(benzyloxy)benzoic acid
          C10H12N2   160.220    5-methoxytryptamine
화살표위  C10H15N6O+ 235.271    HATU      ← 예전에는 통째로 사라지던 자리
          C6H15N     101.193    Triethylamine
용매      CH2Cl2                Dichloromethane (부피 행으로)
생성물    C24H22N2O2 370.452    이론 수율 0.812 g
```

화살표 위 종의 분류(용매냐 시약이냐)는 **추측하지 않는다.** 닫힌 용매 목록에
있으면 부피 행, 아니면 당량 행으로 간다. "작고 관능기 없으면 용매겠지" 같은
추정을 넣으면 진짜 시약이 조용히 당량 계산에서 빠지는데, 그건 한 줄 옮기는
수고보다 훨씬 나쁘다.

### E-1 을 고치다 더 큰 것이 나왔다 — 반응식이면 물성 계산이 죽어 있었다

Ketcher 3.15 의 `getMolfile()` 은 **반응 화살표가 있으면 예외를 던진다**
(`The structure cannot be saved as *.MOL due to reaction arrows.`). 그 예외를
빈 `catch` 가 삼키고 있었다. 결과:

> 화살표를 놓는 순간, 분자식·분자량이 **아무 설명 없이 빈칸이 됐다.**

이 PoC 가 증명해야 하는 단 하나("구조를 넣으면 즉시 분자식·분자량")가, 재단이
가장 중요하게 보는 합성 흐름에서 정확히 죽어 있었던 것이다. 회신에는 이 항목이
없었지만 같은 뿌리라 함께 고쳤다. 이제 반응식이면 **생성물의 물성**을 보여
주고(합성 중 화면에 있어야 할 숫자), 어느 경로로 계산했는지 화면에 밝힌다
(`RDKit · reaction`).

같은 빈-`catch` 패턴이 검색 패널과 재고 패널에도 있다 — 거기서는 반응식일 때
"구조를 그리세요"라는 **틀린 안내**가 뜬다. 후속 과제로 남긴다.

### E-3. HATU 불러오기는 이미 있었다 — 그런데 등록된 구조가 HATU 가 아니었다

> "레드윗에서는 직접 그리는 방식밖에 안 되는 것 같습니다."

기능은 있다. 상단 도구줄의 **`Reagents…`** 에서 이름·CAS·구조로 찾아 캔버스에
넣는다. HATU 와 TEA 모두 등록부에 있고 삽입도 된다. 즉 **없는 게 아니라 못
찾으신 것**이고, 그건 저희 UI 잘못이다 — 이름을 `Reagents…` 대신 "시약 불러오기"
로 바꾸고 캔버스 빈 화면에서도 안내하도록 고치겠다.

다만 확인하다 더 나쁜 것을 찾았다. **등록부의 HATU 구조가 실제로는 HBTU 였다.**

```
등록돼 있던 SMILES   CN(C)C(On1nnc2ccccc21)=[N+](C)C   C11H16N5O+  234.28  ← 벤조트리아졸 = HBTU
참값 (HATU)          CN(C)C(On1nnc2cccnc21)=[N+](C)C   C10H15N6O+  235.27  ← 아자벤조트리아졸
```

고리에 질소 하나가 빠져 있었다. 불러오기가 **동작할수록 틀린 구조가 조용히
노트에 남는** 상태였다. HATU 를 바로잡고 HBTU 를 별도 항목으로 추가했으며,
이름과 구조가 어긋나면 실패하는 테스트를 붙였다.

### E-2. benzene 에 숫자키 1 로 methyl — 상류 Ketcher 동작으로 판정

저희 통합 코드는 **키보드를 전혀 건드리지 않는다.** 프론트엔드 전체에서
`keydown`/`keypress` 처리는 0건이고, Ketcher 설정에도 단축키·결합각 관련
항목을 넘기지 않는다(스톡 Ketcher 3.15.0). 구조 데이터로부터의 좌표 생성은
정확히 120° 로 나온다(toluene·2-methylbutane 실측 모두 120.0°).

따라서 보고하신 현상은 Ketcher 의 **대화형 그리기 경로**에서 일어나는 상류
동작이다. 다만 자동화로는 그 경로를 재현하지 못했다 — **정확한 키 순서나 짧은
화면 녹화를 주시면** 상류에 정식으로 보고하고, 그동안의 우회책(시약 불러오기로
치환기를 붙이는 방법)을 안내드리겠다. 재현 없이 고쳤다고는 적지 않는다.

### N-1 / N-3. 반응식 블록과 절차 자동 삽입

**N-1 은 계산 쪽이 끝났다.** 반응식을 반응물·화살표 위 시약·생성물로 쪼개
각각의 분자식·분자량을 내는 경로가 위에서 검증됐다. 남은 것은 연구노트의
"재료 및 시약" 자리에 지금 들어가 있는 **단일 구조 블록을 반응식 블록으로**
바꾸는 화면 작업이다. 새 계산이 필요하지 않으므로 구현 가능하다.

**N-3 도 가능하다.** 퍼킨엘머의 "preparation 보라색 글씨"에 해당하는 것을
저희는 이미 갖고 있다 — 본문에서 `@` 를 치면 시약·시료·장비를 그 자리에 넣는
멘션 기능이다. 지금은 재고 항목만 대상인데, 여기에 **위 반응식의 종(반응물·
생성물·용매)과 반응 조건(온도)** 을 대상으로 추가하면 된다. 요청하신 우클릭
방식도 같은 목록을 띄우면 되므로 함께 붙일 수 있다. 삽입된 것은 글자가 아니라
살아 있는 참조라, 위에서 이름을 바꾸면 절차 문장도 따라 바뀐다.

### N-2. 이름 영문화 — 완료

> "triethylamine 을 트리에틸아민이라고 한글로 쓸 이유는 없습니다."

맞는 지적이라 그대로 반영했다. 시약 표뿐 아니라 목적·절차 **문장 안의
화합물명까지** 영문으로 바꿨다(문장은 한글, 물질명은 영문 — 합성 노트의 꼴).

```
트리에틸아민        → Triethylamine
탄산칼륨 (무수)     → Potassium carbonate (anhydrous)
디클로로메탄        → Dichloromethane
5-메톡시트립타민    → 5-Methoxytryptamine
"인돌 아민과 4-벤질옥시벤조산의 커플링"
   → "5-Methoxytryptamine 과 4-(benzyloxy)benzoic acid 의 커플링"
```
